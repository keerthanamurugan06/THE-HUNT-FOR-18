# THE HUNT FOR 18 – Final Logical Database Design

> **Implementation note (27 November 2026):** Migration `20261127180000_round2_password_breaker.sql` implements an event-scoped six-slot question set, private bcrypt-hashed challenge/phrase answers, organizer configuration RPCs, per-team order/progress, server validation and victim unlock RPCs. It is applied and hosted-tested on test project `bfzlszktufjqlfiyknga` only. See `docs/ROUND_2.md` for verified results and remaining browser review. No production operation was performed.

## 1. Purpose and Scope

This document defines the approved logical database design for THE HUNT FOR 18. It is
the basis for later Supabase migrations and server-side functions; it is not a SQL
migration and must not be executed as one.

PostgreSQL through Supabase is the authoritative source for event configuration,
authentication references, team state, gameplay progress, submissions, validation,
scores, qualification and timer state. Supabase Auth owns user credentials and
identities; application tables store only the references and authorization data
needed by the application.

The design follows the confirmed four-round storyline:

- Rounds 1–3 progressively reveal victim-related investigation information.
- The final round connects the investigation and identifies the killer.
- Round 3 remains extensible because its gameplay is not finalized.

All identifiers are UUIDs unless otherwise stated. All timestamps are timezone-aware
UTC timestamps. Every table exposed through Supabase APIs has Row Level Security
(RLS) enabled.

## 2. Schema Conventions

- Primary keys are UUIDs generated by the database.
- Foreign keys use restrictive or cascading behavior deliberately: historical
  submissions, score transactions and audit records must not be orphaned or
  silently deleted.
- `created_at` and `updated_at` are maintained in UTC.
- Status and type values use constrained enums or equivalent check constraints.
- JSONB is used only for genuinely flexible configuration, such as a future
  round's configuration or variant-specific rules. It does not replace relations
  for teams, progress, submissions, evidence or scoring.
- Participant-readable records contain no answer keys, hidden words, killer
  identity or other unreleased secrets.
- Configuration is versioned and frozen when a round starts. Frozen records are
  immutable to participants and may be changed only through an organizer operation
  that is recorded in the audit log.

## 3. Logical Schema Groups

### 3.1 CORE

#### `events`

One event record for the investigation.

- `id`, `name`, `event_date`, `duration_minutes`, `status`
- `timezone` for presentation only; persisted event timestamps remain UTC
- `created_at`, `updated_at`

The current event is scheduled for 28 November 2026 and has a provisional
120-minute duration. The organizer may configure the final schedule.

#### `rounds`

Defines the four rounds belonging to an event.

- `id`, `event_id` (foreign key), `round_number`, `round_name`
- `duration_minutes`, `status`, `display_order`
- `starts_at`, `ends_at` when activated
- `created_at`, `updated_at`

Use a unique constraint on `(event_id, round_number)` and on
`(event_id, display_order)`. A round can be visible while locked, but participant
access is controlled by server-side authorization.

#### `round_config`

Versioned, organizer-managed configuration for a round.

- `id`, `round_id` (foreign key), `version`
- `configuration` (JSONB) for approved flexible settings
- `is_frozen`, `frozen_at`, `frozen_by`
- `created_at`, `updated_at`

Only one current configuration is active for a round. A frozen configuration cannot
be edited in place.

### 3.2 IDENTITY AND REGISTRATION

#### `teams`

The participant team's application record.

- `id`, `event_id` (foreign key), `team_code`, `team_name`, `status`
- `auth_user_id` (unique foreign key to the internal Supabase Auth user)
- `access_code_hash` (never the plaintext access code)
- `created_at`, `updated_at`

Use a unique constraint on `(event_id, team_code)` and on `auth_user_id`.
The one-team/one-internal-account model is enforced by a privileged provisioning
operation.

#### `team_members`

The two participants registered to a team.

- `id`, `team_id` (foreign key), `participant_name`, `participant_email`
- `auth_user_id` when an individual identity is needed (nullable)
- `created_at`, `updated_at`

Use a unique constraint on `(team_id, participant_email)` where an email is
provided. A transaction or database constraint/trigger must enforce the approved
maximum of two members per team.

#### `organizer_roles`

Maps Supabase Auth users to organizer permissions.

- `id`, `user_id` (foreign key to Supabase Auth), `role`
- `created_at`, `updated_at`

Roles and privileged actions are checked server-side. The frontend is not an
authorization boundary.

#### `registration_requests` (superseded proposal)

This table appeared in an earlier database-design draft. It is not part of the
current approved flow: participants cannot self-register, and organizers provision
team identities directly. Do not implement or expose this table unless the project
owner explicitly changes that decision.

### 3.3 GAMEPLAY

#### `questions`

Participant-readable question or prompt metadata.

- `id`, `round_id` (foreign key), `question_type`
- `question_content` (JSONB), `points`, `difficulty`
- `display_order`, `status`, `created_at`, `updated_at`

This table does not contain authoritative answers or hidden output.

#### `protected_answer_records`

Server-only answer and validation material for question-based gameplay.

- `id`, `question_id` (unique foreign key), `protected_answer`
- `validation_config` (JSONB), `created_at`, `updated_at`

RLS denies participant access. Server-side validation functions read this table
without returning its contents.

#### `sudoku_puzzle_definitions`

Participant-readable definitions for Round 1's 9x9 Sudoku variants.

- `id`, `round_id` (foreign key), `original_puzzle_id` (stable logical ID)
- `variant_type` (classic, jigsaw, windoku/hyper, anti-knight, anti-king or
  another approved variant)
- `givens`, `variant_rules` (JSONB)
- `jigsaw_regions` (JSONB, required for Jigsaw variants)
- `points`, `difficulty`, `status`, `created_at`, `updated_at`

`givens` stores the starting grid. `variant_rules` stores only rules specific to
the selected variant. Jigsaw region configuration is separate from the solution
and is validated before a puzzle is published.

#### `protected_sudoku_solutions`

Server-only solutions for Sudoku definitions.

- `id`, `puzzle_definition_id` (unique foreign key)
- `solution_grid`, `validation_metadata` (JSONB)
- `created_at`, `updated_at`

The solution is never selected by participant policies or returned by a validation
endpoint. A server-side validator verifies that the givens, variant rules and
solution are valid and uniquely solvable as required by the approved puzzle.

#### `team_sudoku_assignments`

Team-specific display ordering for the shared Round 1 puzzle collection.

- `id`, `team_id` (foreign key), `puzzle_definition_id` (foreign key)
- `display_position`, `original_puzzle_id`
- `created_at`

Use unique constraints on `(team_id, puzzle_definition_id)` and
`(team_id, display_position)`. `original_puzzle_id` is preserved when the
display order is randomized and is the key used to associate evidence.

#### `round_2_challenge_definitions`

Participant-readable metadata and content for the six Round 2 challenges.

- `id`, `round_id` (foreign key), `original_challenge_id` (stable logical ID)
- `challenge_content` (JSONB)
- `round_1_dependency` (JSONB or nullable foreign-key reference as finalized)
- `attempt_limit`, `points`, `status`, `created_at`, `updated_at`

The six challenge records are validated by a round configuration operation. The
exact dependency representation remains pending until the Round 1 evidence
contract is finalized.

#### `team_round_2_challenge_assignments`

Team-specific display ordering for the six Round 2 challenges.

- `id`, `team_id` (foreign key), `challenge_id` (foreign key)
- `original_challenge_id`, `display_position`, `created_at`

Use unique constraints on `(team_id, challenge_id)` and
`(team_id, display_position)`. The original challenge ID is preserved when the
display order is randomized.

#### `protected_round_2_challenge_secrets`

Server-only secrets for each Round 2 challenge.

- `id`, `challenge_id` (unique foreign key)
- `protected_answer`, `hidden_word`, `validation_config` (JSONB)
- `created_at`, `updated_at`

The hidden word is revealed only by a successful server-side challenge validation.
The final phrase is also validated server-side and must not be returned before
the phrase is correct. Final phrase storage may be attached to the round's
protected configuration rather than duplicated per challenge.

#### `maze_level_definitions`

The shared, organizer-managed final-round maze definition.

- `id`, `round_id` (foreign key), `version`, `map_definition` (JSONB)
- `level_order`, `status`, `created_at`, `updated_at`

The definition supports the confirmed shared maze, visible map, routes,
checkpoints and possible challenge/evidence locations without deciding the
unapproved number or arrangement of levels.

#### `protected_final_round_configuration`

Server-only final-round validation and story configuration.

- `id`, `round_id` (unique foreign key), `maze_definition_id` (foreign key)
- `checkpoint_rules` (JSONB), `challenge_validation` (JSONB)
- `protected_killer_identity`, `protected_final_answer`
- `validation_config` (JSONB), `is_frozen`, `created_at`, `updated_at`

The killer identity and final answer are never exposed through participant
queries. A server-side final-validation function checks the team's authorized
evidence and submission, records the result, and returns only the outcome.
No specific maze mechanics or Round 3 mechanics are encoded here before approval.

### 3.4 TEAM ACTIVITY

#### `submissions`

An immutable participant submission attempt.

- `id`, `team_id` (foreign key), `round_id` (foreign key)
- `question_id`, `challenge_id` or final-round target as applicable
- `submission_value` (JSONB), `idempotency_key`
- `submitted_at`, `status`

Use a unique constraint on `(team_id, idempotency_key)` and reject submissions
outside the server-authoritative round window according to the final deadline
policy. Accepted submissions remain stored after expiry.

#### `submission_results`

The authoritative result of a submission.

- `id`, `submission_id` (unique foreign key), `is_correct`
- `points_awarded`, `validation_details` (JSONB), `validated_at`
- `validated_by` or validation function version

Only trusted server-side validation can create this record. Corrections create an
audited adjustment or replacement transaction; the original result is not erased.

#### `evidence`

Investigation evidence that may be unlocked by approved gameplay outcomes.

- `id`, `event_id` (foreign key), `source_round_id` (foreign key)
- `source_original_puzzle_id` (nullable), `source_challenge_id` (nullable)
- `title`, `evidence_type`, `display_order`
- `created_at`, `updated_at`

The source original puzzle ID, not a team display position, identifies Round 1
evidence. This table contains participant-readable metadata only; evidence
content is stored separately.

#### `protected_evidence_content`

Server-only content for an evidence item.

- `id`, `evidence_id` (unique foreign key)
- `protected_content`, `created_at`, `updated_at`

RLS denies participant access to this table. A secure server-side function must
verify the authenticated team's unique `team_evidence` unlock record before
returning this content. Protected evidence must never be exposed through
ordinary participant queries.

#### `team_evidence`

Evidence unlocked for a team.

- `id`, `team_id` (foreign key), `evidence_id` (foreign key), `unlocked_at`
- `unlock_source_submission_id` (nullable foreign key), `unlock_metadata` (JSONB)

Use a unique constraint on `(team_id, evidence_id)`. Unlocking is an atomic
server-side operation, so retries cannot create duplicate unlocks.

#### `team_round_progress`

Durable team state for each round.

- `id`, `team_id` (foreign key), `round_id` (foreign key)
- `status`, `progress_data` (JSONB), `last_activity_at`
- `created_at`, `updated_at`

Use a unique constraint on `(team_id, round_id)`. JSONB stores only state that is
specific to the round; authoritative submissions, results, evidence, scores and
final validation remain relational.

For the final round, `progress_data` supports the shared maze's team-specific
player position, reached checkpoints, completed challenges and recovered evidence
references. These values are updated through server-side operations and must not
be trusted as proof of completion.

### 3.5 SCORING AND QUALIFICATION

#### `score_ledger`

Append-only authoritative score transactions.

- `id`, `event_id` (foreign key), `team_id` (foreign key), `round_id` (foreign key)
- `submission_id` (nullable foreign key), `transaction_type`
- `points_delta`, `idempotency_key`, `reason`, `created_at`, `created_by`

Use a unique constraint on the operation's idempotency key and appropriate
uniqueness for a submission's scoring transaction. No update or delete is allowed
to participants; corrections append compensating transactions and are audited.

#### `team_round_score_totals` (derived view or protected read model)

The per-team, per-round total derived from `score_ledger`.

- `team_id`, `round_id`, `total_points`

Prefer a view or server-maintained read model rather than a second mutable source
of truth. Any materialized total must be recomputable from the append-only ledger.
If implemented as a PostgreSQL view, use `security_invoker = true` where
supported so the view does not bypass underlying RLS. Otherwise, expose totals
through an appropriately authorized server-side function. Participants must see
only score information permitted by an associated released leaderboard; the
totals view or function must not become an unrestricted score endpoint.

#### `leaderboard_releases`

Controls publication of a completed round's leaderboard.

- `id`, `event_id` (foreign key), `round_id` (foreign key)
- `status`, `released_by`, `released_at`, `release_version`
- `release_metadata` (JSONB), `created_at`

Leaderboards are not live. Participant queries can see only a released version
for their authorized event and round.

#### `qualifications`

Authorizes a team to enter a later round, including the final round.

- `id`, `team_id` (foreign key), `round_id` (foreign key)
- `qualified`, `decision_type`, `decided_by`, `decided_at`, `notes`
- `created_at`, `updated_at`

Use one current qualification decision per team and round, while retaining
revisions through audit history. Qualification and final-round unlocking are
server-side operations. Qualification for optional Round 4 is the top six teams
by cumulative Round 1–3 scores. Preliminary-round access is not gated by prior
completion. Exact marks remain pending; never invent scoring values.

### 3.6 EVENT CONTROL

#### `timers`

The server-authoritative timer state for a round.

- `id`, `round_id` (unique foreign key), `status`
- `started_at`, `ends_at`, `paused_at`, `accumulated_paused_seconds`
- `updated_at`, `updated_by`

Timer start, pause, resume, extension and manual end are authorized
server-side operations. All teams read the same authoritative timestamps.

#### `event_audit_logs`

Append-only record of important administrative and privileged operations.

- `id`, `event_id` (foreign key), `actor_user_id`
- `action`, `entity_type`, `entity_id`
- `old_values` (JSONB), `new_values` (JSONB), `metadata` (JSONB)
- `created_at`

Record configuration freezes and changes, registration decisions, timer changes,
submission corrections, score adjustments, qualification decisions, evidence
unlocks, final-round authorization and leaderboard releases. Participants cannot
insert, update or delete audit records.

## 4. Relationships and Integrity Rules

- One event has four rounds, and each round has versioned configuration.
- One team belongs to one event, has one internal Auth account and has at most two
  team members.
- A team has one progress record per round and may have many submissions.
- A submission has at most one authoritative result.
- A team can unlock each evidence item at most once.
- Round 1 evidence references the original puzzle ID, regardless of team display
  order.
- Round 2 has six challenge definitions and a team-specific randomized display
  order; hidden words and answers remain protected.
- A team has at most one current qualification decision per round.
- Score totals are derived from immutable score transactions.
- A round has one authoritative timer record.
- Multi-table operations use transactions, especially submission validation,
  scoring, evidence unlocking, qualification and final-round authorization.
- Foreign keys, unique constraints, check constraints and indexes enforce event,
  team, round and idempotency boundaries.

Recommended indexes include foreign-key columns, `(team_id, round_id)` activity
lookups, submission idempotency keys, evidence source identifiers, score-ledger
team/round queries and timer round lookups.

## 5. Security and Access Model

### Participant access

- RLS is enabled on every participant-accessible table.
- Policies derive the participant's team from the authenticated Supabase Auth
  identity and permit only that team's records.
- Participants may read their team profile, allowed round content, their own
  progress, their submissions/results, evidence metadata and content returned by
  the unlock-verified server-side evidence function, and released leaderboards.
- Participants may not read protected answer records, Sudoku solutions, Round 2
  secrets, protected final configuration, protected evidence content, unreleased
  evidence, score-ledger internals or audit logs.
- Participant writes go through server-side functions or tightly scoped inserts;
  authoritative validation, scoring and unlocking never trust browser values.

### Organizer access

- Organizer roles are verified server-side for configuration, moderation, timer,
  score, qualification, release and final-round operations.
- Organizer-only functions may read protected content and execute privileged
  transitions, but must record consequential changes in `event_audit_logs`.
- Service-role credentials are never sent to or embedded in the frontend.

### Server-side operations

The application uses secure database functions or Supabase Edge Functions for:

- organizer-authorized team provisioning (public participant registration is disabled);
- round activation, timer control and configuration freezing;
- answer/submission validation and attempt-limit enforcement;
- idempotent evidence unlocking and unlock-verified evidence retrieval;
- score-ledger transactions and RLS-preserving score-total access;
- qualification and final-round unlocking;
- final killer-identification validation;
- leaderboard release and authorized organizer corrections.

## 6. Pending Decisions

The following remain explicitly unresolved and must be approved before migrations
or gameplay-specific implementation:

- Whether participant registration requests should ever be introduced later; the
  current approved flow is organizer provisioning and requires no participant email.
- Final question, evidence, answer and protected-content formats.
- Round 1 puzzle count, difficulty distribution, points, attempt limits and
  penalties.
- The exact Round 1 variant rule schema and final puzzle collection.
- Round 2 challenge contents, hidden words, final phrase, individual attempt
  limits, points and the exact Round 1 evidence dependency.
- All Round 3 gameplay, data fields, validation, scoring, penalties and output.
  No Round 3 mechanics are assumed by this design.
- Final maze level count, layout, checkpoints, mini-challenges, trap behavior,
  movement controls, scoring and tie-breakers.
- Final-round evidence requirements, answer format and killer-identification
  validation rules.
- Qualification count and qualification policy.
- Data retention and event cleanup policy.
- Whether any materialized score read model is required instead of the derived
  view.

No unresolved decision may be silently converted into an event rule or gameplay
mechanic.

## 7. Implementation Boundary

This finalized logical design does not create migrations, execute SQL or change
application code. Before implementation, create version-controlled Supabase
migrations from this design, define and test RLS policies, implement the
server-side operations, and verify participant isolation and organizer privileges
with representative accounts.
